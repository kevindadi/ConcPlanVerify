\section{Motivation}
\label{sec:motivation}

% 本节通过一个简单的唤醒丢失示例来说明该流水线的动机.该示例突显了为什么原始源代码不适合直接进行并发推理,为什么Petri网式的验证模型对穷举分析很有吸引力,以及为什么需要在两者之间引入像Cir这样的中间表示.
This section illustrates the motivation of the pipeline through a small lost wake-up example. The example highlights why raw source code is a poor object for direct concurrency reasoning, why a Petri-net-style verification model is attractive for exhaustive analysis, and why an intermediate representation such as \textsc{Cir} is needed between the two.

\subsection{A Lost Wake-up Example}
\label{subsec:running-example}

% 图~\ref{fig:running-rust}展示了一个简单的Rust程序,其中包含一个丢失唤醒信号的bug.工作线程会等待一个条件变量,直到共享标志\texttt{ready}变为true.通知线程获取了同一个互斥锁,调用\texttt{notify\_one},然后才写入\texttt{ready := true}.如果通知发生在工作线程进入等待状态之前,则信号丢失,工作线程可能会无限期阻塞.程序可以编译通过,因为该缺陷并非类型或所有权错误,而是并发顺序错误.
Figure~\ref{fig:running-rust} shows a simple Rust program with a lost wake-up bug. The worker thread waits on a condition variable until the shared flag \texttt{ready} becomes true. The notifier thread acquires the same mutex, calls \texttt{notify\_one}, and only then writes \texttt{ready := true}. If the notification occurs before the worker has entered the wait state, the signal is lost and the worker can block forever. The program compiles cleanly because the defect is not a type or ownership violation; it is a concurrency-ordering bug.

\begin{figure}
\begin{lstlisting}[language=rust, basicstyle=\small\ttfamily, frame=single]
fn worker(shared: Arc<(Mutex<bool>, Condvar)>) {
let (m, cv) = &*shared;
let mut g = m.lock().unwrap();
while !*g {
g = cv.wait(g).unwrap();
}
}

fn notifier(shared: Arc<(Mutex<bool>, Condvar)>) {
let (m, cv) = &*shared;
let mut g = m.lock().unwrap();
cv.notify_one();   // BUG: notify before flag update
*g = true;         // too late
}
\end{lstlisting}
\caption{A condition-variable signal-loss bug in Rust.}
\Description{A Rust example with two functions. The worker locks a mutex and waits on a condition variable until a shared boolean becomes true. The notifier locks the same mutex, calls notify\_one on the condition variable, and only then writes the boolean flag, illustrating a lost wake-up bug.}
\label{fig:running-rust}
\end{figure}

% 图~\ref{fig:running-cir} 展示了 Cir 中的相同示例.这种抽象的目的并非保留所有源代码级细节,而是精确保留对并发推理至关重要的信息:哪些资源是共享的,哪个锁保护哪个变量,线程在哪里等待和通知,以及如果设计出现问题应该归咎于哪个语句标识符.显式全局名称 \texttt{m0}、\texttt{cv0} 和 \texttt{ready} 消除了别名重构.显式保护声明使预期的锁定机制清晰可见.\texttt{sid} 值创建了用于诊断和修复的稳定锚点.
Figure~\ref{fig:running-cir} shows the same example in \textsc{Cir}. The purpose of this abstraction is not to preserve all source-level detail, but to preserve exactly the information that matters for concurrency reasoning: which resources are shared, which lock protects which variable, where threads wait and notify, and which statement identifier should be blamed if the design goes wrong. The explicit global names \texttt{m0}, \texttt{cv0}, and \texttt{ready} eliminate alias reconstruction. The explicit protection declaration makes the intended locking discipline visible. The \texttt{sid} values create stable anchors for diagnosis and repair.

\begin{lstlisting}[basicstyle=\small\ttfamily, frame=single]

cv0:   { kind: Condvar, paired_with: m0 }
ready: { kind: Var, type: Bool, init: false }

ready: [m0]

worker:
body:
- { sid: w1, op: {lock: m0}, transfer: {next: w2} }
- { sid: w2, op: {read: ready}, transfer: {branch: {...}} }
- { sid: w3, op: {wait: {cv: cv0, mutex: m0}}, ... }
notifier:
body:
- { sid: n1, op: {lock: m0}, ... }

\end{lstlisting}
\caption{\textsc{Cir} for the running example, featuring global naming and explicit protection.}

% 经过验证的 \textsc{Cir} 在本地被转换为 \textsc{Cvn}.图~\ref{fig:translation-example} 描绘了为 \texttt{notifier} 函数生成的片段.重点不在于具体的符号,而在于该错误很容易被表达为一个可达性问题.通知操作包含一个正常分支,用于唤醒等待者;以及一个丢失信号分支,当等待者数量为零时,该分支会推进控制权.对该网络进行本地可达性分析可以快速生成一个见证,其中锚定在 \texttt{n2} 的转换在工作节点到达锚定在 \texttt{w3} 的等待点之前触发.换句话说,一旦模型形式正确,形式化引擎就很容易找到该错误.
The validated \textsc{Cir} is translated locally into a \textsc{Cvn}. Figure~\ref{fig:translation-example} sketches the fragment generated for the \texttt{notifier} function. The important point is not the exact notation, but the fact that the bug becomes easy to express as a reachability question. The notify action has a normal branch that wakes a waiter and a lost-signal branch that advances control when the waiter count is zero. A local reachability analysis over this net can quickly produce a witness in which the transition anchored at \texttt{n2} fires before the worker reaches the waiting point anchored at \texttt{w3}. In other words, once the model is in the right form, the bug is easy for the formal engine to find.

% 因此,挑战不在于Petri网式可达性不足,而在于管道的两端都不是LLM的理想主要接口.原始Rust代码包含别名、所有权、API惯用法和表示细节,这些都掩盖了预期的并发结构[参考文献:Engler2003RacerX, Pratikakis2006Locksmith, Naik2006StaticRaceJava, Flanagan2003Atomicity, Boyapati2002Ownership].原始验证网则处于另一个极端:它非常适合局部穷举分析[参考文献:Murata1989PetriNets, Holzmann1997SPIN, Esparza2008Unfoldings],但对于语义推理和迭代修复而言,它过于底层且过于冗长.Cir则处于中间位置.它足够短,LLM 可以直接进行推理;足够明确,可以显示并发意图;结构足够清晰,可以机械地转换为验证模型.
The challenge, then, is not that Petri-net-style reachability is inadequate; it is that neither end of the pipeline is a good primary interface for the LLM. Raw Rust code contains aliasing, ownership, API idioms, and representation detail that obscure the intended concurrency structure \cite{Engler2003RacerX,Pratikakis2006Locksmith,Naik2006StaticRaceJava,Flanagan2003Atomicity,Boyapati2002Ownership}. A raw verification Petri net sits at the opposite extreme: it is ideal for local exhaustive analysis \cite{Murata1989PetriNets,Holzmann1997SPIN,Esparza2008Unfoldings}, but too low-level and too verbose to serve as the main object of semantic reasoning and iterative repair. \textsc{Cir} occupies the middle ground. It is short enough for the LLM to reason about directly, explicit enough to make concurrency intent visible, and structured enough to be translated mechanically into a verification model.

% 这种分工对于迭代修复尤为重要.LLM 无需消耗令牌来模拟状态空间搜索或遍历整个网络.相反,本地验证器将 Cir 转换为 Cvn,执行非提示可达性分析,并返回一个简洁的诊断包:错误类型、见证跟踪、语句标识符,以及基于标记的资源持有者和等待者摘要.然后,LLM 仅修改相关的 Cir 切片.这就是整体设计的动机:在语义意图至关重要的地方使用 LLM,在详尽交错分析至关重要的地方使用 Petri 网后端,并将 Cir 置于中间作为共享对象,以保持双方的简洁性和可分析性.
This division of labor is especially important for iterative repair. The LLM need not spend tokens simulating state-space search or traversing a full net. Instead, the local verifier translates \textsc{Cir} to \textsc{Cvn}, performs reachability analysis off-prompt, and returns a compact diagnostic package: bug kind, witness trace, statement identifiers, and a marking-derived summary of who holds which resource and who is waiting for what. The LLM then revises only the relevant \textsc{Cir} slice. This is the motivation for the overall design: use the LLM where semantic intent matters most, use the Petri-net back-end where exhaustive interleaving analysis matters most, and place \textsc{Cir} in the middle as the shared object that keeps both sides concise and analyzable.
