\section{Analysis and Repair}
\label{sec:analysis-repair}

% 这节要把重点放在“分析结果如何转成可修复诊断”，而不是把 reachability 本身当作创新点。
This section explains how \textsc{Cvn} analysis results are converted into repair-oriented feedback for the LLM. The underlying reachability and SCC analyses are standard \cite{Godefroid1997VeriSoft,Flanagan2005DPOR,Musuvathi2008FairStateless,Esparza2008Unfoldings}. The main contribution here is the design of a diagnostic interface between the verifier and the LLM: what information is extracted from a bug state, why that information is necessary for repair, and how it is assembled into a prompt that supports local revision rather than whole-model regeneration.

\subsection{Reachability-Based Bug Detection}
\label{subsec:bug-patterns}

% 先交代分析引擎的最基本语义：unknown guard 两边都要探索，因此整体是保守过近似。
Given a translated \textsc{Cvn}, the verifier performs exhaustive reachability analysis from the initial state. If a guard evaluates to $\mathsf{unknown}$ under the current valuation, both outgoing possibilities are explored. The resulting search is therefore a conservative over-approximation: it never suppresses a behavior that would be possible under a concrete execution, though it may introduce spurious paths when unknown values remain.

% 这里简要列出 bug 类别，但不过多渲染“检测算法本身”，因为这不是本文最想卖的点。
We detect five categories of violations as predicates over the reachable state graph:
\begin{itemize}[leftmargin=1.5em]
    \item \emph{Deadlock ($\kappa_{dl}$):} a non-terminal state with no enabled transition.
    \item \emph{Signal loss ($\kappa_{sl}$):} a notification transition fires when the corresponding waiter count is zero.
    \item \emph{Livelock ($\kappa_{ll}$):} a non-terminal SCC that permits infinite internal cycling without progress to return places.
    \item \emph{Starvation ($\kappa_{st}$):} an SCC in which one thread remains perpetually blocked from progress while other threads continue to move.
    \item \emph{Channel block ($\kappa_{cb}$):} a deadlock involving a receive transition whose required channel token can no longer be produced.
\end{itemize}

% 重点转向下一步：检测到 bug 并不够，真正困难的是怎么把 bug state 变成 LLM 能用的修复上下文。
These predicates are sufficient for classification, but classification alone is not enough for repair. A label such as ``deadlock'' or ``signal loss'' does not tell the LLM where the execution got stuck, which statements created the bad state, or which local rewrite is least likely to damage unrelated behavior. The repair problem therefore begins after detection, not before it.

\subsection{Repair-Oriented Diagnostics}
\label{subsec:counterexample}

% 先明确说“不要把原始 marking 直接扔给 LLM”，而是要做结构化提炼。
When a violation is found, the verifier does not return the raw reachable-state graph or a full marking dump. Those objects are faithful to the net, but they are poorly matched to the needs of a repair model. Instead, the verifier constructs a compact diagnostic payload that preserves the information needed for repair while discarding low-level noise.

% 给出正式定义，把本文需要的诊断字段系统化。
\begin{definition}[Repair-oriented diagnostic]
A repair-oriented diagnostic is a tuple
\[
\mathcal{D} = (\kappa,\; \pi_{\mu},\; \Sigma_{\mathit{state}},\; \Sigma_{\mathit{wait}},\; \Lambda,\; \Gamma_{\mathit{ctx}},\; H)
\]
where $\kappa$ is the bug kind, $\pi_{\mu}$ is an anchored witness trace, $\Sigma_{\mathit{state}}$ is a marking-derived state summary, $\Sigma_{\mathit{wait}}$ is a wait/ownership summary, $\Lambda$ is the relevant \textsc{Cir} slice, $\Gamma_{\mathit{ctx}}$ is the set of preservation constraints, and $H$ is a bug-specific repair hint.
\end{definition}

% 逐项解释这些字段为什么需要，强调 marking 和 sequence 都是必要但不能原样给。
Each field serves a different purpose.
\begin{itemize}[leftmargin=1.5em]
    \item \emph{Bug kind $\kappa$.} This determines the high-level repair mode. Deadlock, signal loss, and starvation call for different kinds of edits.
    \item \emph{Anchored witness trace $\pi_{\mu}$.} This is the sequence of \textsc{Cir} statement identifiers encountered on a witness path to the bug state. It localizes the execution history in terms the LLM can edit.
    \item \emph{State summary $\Sigma_{\mathit{state}}$.} This is a compact rendering of the final bug state: which thread is currently at which \textsc{Cir} statement, which resource counts are available, and whether the system is globally blocked or still moving.
    \item \emph{Wait/ownership summary $\Sigma_{\mathit{wait}}$.} This extracts the relations that matter most for repair: which thread holds which resource, which thread is waiting for which resource or condition, and which wait-count predicates triggered the bug classification.
    \item \emph{Relevant \textsc{Cir} slice $\Lambda$.} This is a bounded local window around the implicated statement identifiers. It reduces the search space by telling the LLM which part of the artifact should be edited.
    \item \emph{Preservation constraints $\Gamma_{\mathit{ctx}}$.} These specify what must remain true after repair: preserve resource names, preserve thread structure, and ultimately preserve business goals.
    \item \emph{Repair hint $H$.} This is a bug-specific hint produced by the verifier, such as ``enforce a consistent lock order'' or ``update the predicate before notification.''
\end{itemize}

% 强调 marking 本身必需，但 raw marking 不是最佳提示；LLM 更需要从 marking 派生出来的结构化摘要。
The marking is indispensable because it records the exact program state represented by the net. However, the raw marking is not the best prompt format. What the LLM actually needs is the structured interpretation of that marking: the blocked control locations, the held resources, the waiting relationships, and the specific predicate that made the bug visible. The witness sequence is equally important because it explains not only \emph{where} the system is stuck, but also \emph{how it got there}. Together, the witness and the state summary provide both causality and locality.

% 给一个 signal loss 的具体说明，帮助读者理解 diagnostic 到底长什么样。
For the running example, a signal-loss diagnostic would report that the witness trace reaches \texttt{n2} before the worker reaches \texttt{w3}, that the waiter count for \texttt{cv0} is zero at notification time, and that the relevant editable slice contains \texttt{n2} and \texttt{n3}. This is much more actionable than merely stating that a lost wake-up exists somewhere in the model.

\subsection{The Goal-Aware Repair Loop}
\label{subsec:repair-loop-final}

% 修复循环在逻辑上分三层，但顺序很重要：先静态正确，再并发 bug-free，最后 goals reachable。
The repair loop operationalizes the hierarchy introduced in Section~\ref{subsec:repair-tier}. Trivial Layer-1 problems are fixed deterministically when possible. More substantial Layer-1 problems trigger localized regeneration. Layer-2 bugs trigger logic-driven repair using the diagnostic payload above. The crucial ordering choice is that goal checking happens only after the bug search reports no remaining concurrency violation. Otherwise, an unreachable goal might simply reflect a deadlocked execution rather than a semantically incomplete repair.

\begin{algorithm}[t]
\caption{Goal-Aware Generate-Verify-Repair Loop}
\label{alg:repair-goal}
\begin{algorithmic}[1]
\Require Specification $\Psi$, Max iterations $K$
\Ensure Verified \textsc{Cir} $\mathcal{I}$ or Failure
\State $\mathcal{I} \gets \text{LLM.Generate}(\Psi)$
  \Comment{CIR with goals $\Gamma$}
\For{$round = 1$ \textbf{to} $K$}
    \State $\mathcal{E}_{L1} \gets \text{StaticCheck}(\mathcal{I})$
    \If{$\mathcal{E}_{L1} \neq \emptyset$}
        \State Apply Tier-1 or Tier-2 repair;\;
          \textbf{continue}
    \EndIf
    \State $\mathcal{N} \gets \text{Translate}(\mathcal{I})$
    \State $(\mathcal{R},\; \mathcal{B}) \gets \text{Analyze}(\mathcal{N})$
    \If{$\mathcal{B} \neq \emptyset$}
        \State $\mathcal{D} \gets \text{GenDiagnostic}(\mathcal{B}, \mathcal{R})$
        \State $\mathcal{I} \gets \text{LLM.Repair}(\mathcal{I}, \mathcal{D})$
        \State \textbf{continue}
    \EndIf
    \State $\mathcal{U} \gets
      \{\gamma \in \Gamma \mid \nexists\, s \in \mathcal{R}: s \models \gamma\}$
    \If{$\mathcal{U} = \emptyset$}
        \Return $\mathcal{I}$
    \EndIf
    \State $\mathcal{I} \gets \text{LLM.Repair}(\mathcal{I}, \text{GenGoalViolation}(\mathcal{U}))$
\EndFor
\State \Return Failure
\end{algorithmic}
\end{algorithm}

% bug-free 之后再查 goals，这一点要单独讲清楚，因为这是 acceptance criterion 的关键。
This ordering gives every feedback round a single semantic target. If a bug is present, the LLM is asked to remove the bug without yet reasoning about goal reachability. If no bug is present but a goal is unreachable, the LLM is asked to restore missing behavior without being distracted by concurrency faults that have already been resolved.

% goal violation 反馈保留，因为它很好地说明“bug-free 还不够”。

\subsection{Prompt Templates for Logic-Driven Repair}
\label{subsec:repair-templates}

% 用 prompt template 代替原先那张“bug kind -> strategy”的表，因为真正重要的是给 LLM 什么字段、字段为什么必要。
Table~\ref{tab:repair-templates} summarizes the prompt template used for logic-driven repair. The key design principle is that every field should either reduce the search space or protect intended behavior.

\begin{table*}[t]
\caption{Prompt template for \textsc{Cir} repair from a \textsc{Cvn} diagnostic.}
\label{tab:repair-templates}
\centering\small
\begin{tabular}{@{}p{3.0cm}p{4.7cm}p{7.2cm}@{}}
\toprule
\textbf{Prompt field} & \textbf{Instantiated from} & \textbf{Why it is needed} \\
\midrule
Bug kind & Bug predicate $\kappa$ & Selects the repair mode: deadlock, signal loss, starvation, livelock, or channel block require different structural edits. \\
\addlinespace[3pt]
Witness trace (\texttt{sid}) & Anchored trace $\pi_{\mu}$ & Localizes the causal path to the bug state using editable statement identifiers rather than low-level transition names. \\
\addlinespace[3pt]
Bug-state summary & Marking-derived $\Sigma_{\mathit{state}}$ & Tells the LLM where execution is currently stuck: current statement per thread, blocked/non-blocked status, and critical variable values. \\
\addlinespace[3pt]
Held resources & Ownership component of $\Sigma_{\mathit{wait}}$ & Explains which locks, channels, or semaphores are currently preventing progress. \\
\addlinespace[3pt]
Waiting relations & Waiting component of $\Sigma_{\mathit{wait}}$ & Makes the dependency structure explicit: who is waiting for what, and which predicate triggered the diagnosis. \\
\addlinespace[3pt]
Relevant \textsc{Cir} slice & Local window $\Lambda$ & Restricts editing to a small region around implicated statements and reduces unintended rewrites elsewhere. \\
\addlinespace[3pt]
Preservation constraints & $\Gamma_{\mathit{ctx}}$ & Prevents over-repair by requiring resource names, thread roles, and business goals to remain valid. \\
\addlinespace[3pt]
Repair hint & Heuristic $H$ & Provides a stable direction without forcing a single patch, e.g., reorder locks, update predicate before notify, shorten critical section. \\
\addlinespace[3pt]
Output contract & Verifier-defined schema & Forces the model to return only the revised \textsc{Cir} fragment or statement list, keeping the loop local and machine-checkable. \\
\bottomrule
\end{tabular}
\end{table*}

% 给一个具体提示词骨架，展示论文不是只说“给一些错误信息”，而是有一套明确的组织格式。
\begin{figure}[t]
\begin{lstlisting}[basicstyle=\small\ttfamily, frame=single]
Repair task: revise the CIR locally.

Bug kind: SignalLoss
Witness trace (sid): n1 -> n2 -> w1 -> w2 -> w3

Bug-state summary:
- notifier has executed sid n2
- worker has not yet entered wait sid w3
- waiter_count(cv0) = 0 at notification

- mutex m0
- condvar cv0

\end{lstlisting}
\caption{Prompt skeleton for logic-driven \textsc{Cir} repair.}
\Description{A structured repair prompt. It includes the bug kind, witness sid trace, bug-state summary, relevant resources, local CIR slice, preservation constraints, a suggested repair direction, and an output contract requesting only the revised CIR slice.}
\label{fig:repair-prompt}
\end{figure}

% 这里点出 prompt 设计的核心：不是把所有分析结果都给 LLM，而是给“最少但足够”的诊断信息。
The prompt is intentionally compact. It does not serialize the full reachability graph, the full net, or every intermediate marking. Instead, it gives the minimum stateful evidence needed for a local repair: what failed, how the execution reached the failure, what the system looks like at the failure point, and what must be preserved while repairing it. This is the interface that allows a local formal analyzer and a token-bounded LLM to work together effectively.
