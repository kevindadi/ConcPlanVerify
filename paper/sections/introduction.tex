\section{Introduction}
\label{sec:introduction}

% 并发缺陷,例如死锁、信号丢失、饥饿和阻塞协议错误,仍然难以检测和修复,因为它们源于线程间的交互,而非单一的局部控制路径.动态工具可以暴露具体的失败调度,但它们无法排除未探索的交错执行情况[参考文献:Godefroid 1997 VeriSoft, Musuvathi 2008 Heisenbugs, Burckhardt 2010 RandomizedScheduler].原则上,静态技术可以提供更广泛的保证,但它们面临着一个常见的障碍:在推断锁顺序、等待规则或协议合规性之前,分析必须确定哪些操作引用了相同的共享资源,以及哪些同步原语保护了哪些共享状态[参考文献:Engler 2003 RacerX, Flanagan 2000 TypeBasedRace, Flanagan 2003 Atomicity, Boyapati 2002 Ownership, Naik 2006 StaticRaceJava].因此,并发缺陷在实践中仍然代价高昂.它们可能通过广泛的测试隐藏起来,只在生产环境中的某个狭窄时间窗口内出现,正是因为相关的行为分布在线程和调度中,而不是集中在一行明显错误的代码中.
Concurrency bugs such as deadlocks, signal losses, starvation, and blocking protocol errors remain difficult to detect and repair because they arise from interactions among threads rather than from a single local control path. Dynamic tools can expose concrete failing schedules, but they do not rule out unexplored interleavings \cite{Godefroid1997VeriSoft,Musuvathi2008Heisenbugs,Burckhardt2010RandomizedScheduler}. Static techniques can, in principle, provide broader guarantees, yet they face a familiar obstacle: before reasoning about lock ordering, waiting discipline, or protocol compliance, the analysis must determine which operations refer to the same shared resource and which synchronization primitives protect which shared state \cite{Engler2003RacerX,Flanagan2000TypeBasedRace,Flanagan2003Atomicity,Boyapati2002Ownership,Naik2006StaticRaceJava}. Concurrency defects therefore remain costly in practice. They may hide through extensive testing and surface only under a narrow timing window in production, precisely because the relevant behavior is distributed across threads and schedules rather than concentrated in one obviously wrong line of code.

% 难点不仅在于并发代码存在大量的交错执行;还在于源代码级别的推理必须通过层层表示细节来重构资源标识.考虑一个 Rust 风格的程序,其中两个线程各自接收一个 `Arc<(Mutex<State>, Condvar)>` 的克隆.为了确定两个线程是否操作同一个互斥锁-条件变量对,验证器必须追踪该值在堆分配、`Arc::clone`、解构、借用和闭包捕获等过程中的流转过程[参考文献:Boyapati2002Ownership, Pratikakis2006Locksmith, Naik2006StaticRaceJava].如果没有这种标识信息,死锁检测器就无法可靠地构建锁序图,保护检查器也无法可靠地确定对共享变量的访问是否受到预期锁的保护.现有工具通过一些常见的权衡取舍来应对这一障碍:较粗略的分析可以提高可扩展性但会降低精度,更精确的分析通常可扩展性较差,而动态工具通过在运行时观察具体地址来绕过别名重建,但会牺牲覆盖率.在自动化修复工作流程中,这些权衡取舍尤为棘手,因为诊断结果既要足够精确以避免误导修复过程,又要足够实用以指出具体的同步逻辑.
The difficulty is not merely that concurrent code has many interleavings; it is also that source-level reasoning must reconstruct resource identity through layers of representation detail. Consider a Rust-style program in which two threads each receive a clone of an \texttt{Arc<(Mutex<State>, Condvar)>}. To determine whether both threads operate on the same mutex--condvar pair, a verifier must trace the value through heap allocation, \texttt{Arc::clone}, destructuring, borrowing, and closure capture \cite{Boyapati2002Ownership,Pratikakis2006Locksmith,Naik2006StaticRaceJava}. Without that identity information, a deadlock detector cannot reliably build a lock-order graph, and a protection checker cannot reliably determine whether a shared-variable access is guarded by the intended lock. Existing tools cope with this barrier through familiar trade-offs: coarser analyses improve scalability but lose precision, more precise analyses often scale poorly, and dynamic tools bypass alias reconstruction by observing concrete addresses at runtime but sacrifice coverage. These trade-offs become especially painful in an automated repair workflow, where diagnostics must be both precise enough to avoid misleading the repair process and actionable enough to point to specific synchronization logic.

% 本文探索了一种不同的切入点.我们不再要求形式化后端从源代码中精确地重建别名,而是探讨是否可以围绕同步意图重新定义问题.传统的分析方法关注的是实现工件:给定一堆指针、闭包和引用计数句柄,哪些表达式恰好指向同一个对象？然而,对于并发推理而言,一个更有用的问题通常更简单:程序打算使用哪些共享资源,以及哪些锁保护哪些状态？基于大型代码语料库训练的大型语言模型(LLM)通常比模拟精确的底层别名历史更擅长恢复这种高层结构[Chen2021CodeLLMs,Fan2023RepairFromLLMs,Xia2023APRLLMs].读取生产者-消费者设计的LLM无需追踪每个\texttt{Arc::clone}链即可推断出程序围绕一个共享队列、一个保护该队列的互斥锁和一个指示可用性的条件变量运行.因此,我们工作的关键思想并非解决了源代码级别名分析,而是形式化验证层可以设计成不再依赖于精确求解该问题.
This paper explores a different starting point. Instead of asking the formal back-end to reconstruct aliases precisely from source code, we ask whether the problem can be reframed around synchronization intent. Traditional analysis asks a question about implementation artifacts: given this heap of pointers, closures, and reference-counted handles, which expressions happen to denote the same object? For concurrency reasoning, however, a more useful question is often simpler: what shared resources does this program intend to use, and which locks protect which state? Large language models (LLMs), trained on large code corpora, are often better at recovering this higher-level structure than at simulating exact low-level alias histories \cite{Chen2021CodeLLMs,Fan2023RepairFromLLMs,Xia2023APRLLMs}. An LLM reading a producer--consumer design does not need to follow every \texttt{Arc::clone} chain to infer that the program revolves around one shared queue, one mutex protecting it, and one condition variable signaling availability. The key idea of our work is therefore not that source-level alias analysis has been solved, but that the formal verification layer can be designed so that it no longer depends on solving it precisely.

% 这种重新构建引出了我们架构中的第一个形式化模型——并发中间表示(Cir).Cir 是一个面向验证的语句级并发模型,旨在由逻辑逻辑模型(LLM)生成,并供形式化分析引擎使用.每个共享资源都拥有一个唯一的全局名称;锁到变量的保护关系被显式记录;每个语句都携带一个稳定的标识符($\mathsf{sid}$),用于诊断和修复.其结果并非通用编译器中间表示,而是程序并发框架的一个刻意缩小的模型:同步操作、线程创建和加入,以及对共享状态的数据相关控制.算术细节、字符串操作和大多数 I/O 逻辑都被抽象掉了.正是这种缩小使得模型生成变得易于处理.LLM 不需要生成完整的可执行程序;它只需要明确地表达并发架构即可.然后,确定性检查器根据分为 9 个类别的 61 条规则验证生成的工件,在更昂贵的验证阶段之前捕获格式错误或语义不一致的 Cir 工件.
This reframing leads to the first formalism in our architecture, the \emph{Concurrency Intermediate Representation} (\textsc{Cir}). \textsc{Cir} is a verification-oriented, statement-level concurrency model designed to be generated by an LLM and consumed by a formal analysis engine. Every shared resource receives a unique global name; lock-to-variable protection relations are recorded explicitly; and every statement carries a stable identifier ($\mathsf{sid}$) for diagnostics and repair. The result is not a general-purpose compiler IR, but a deliberately narrowed model of the program's concurrency skeleton: synchronization operations, thread creation and joining, and data-dependent control over shared state. Arithmetic details, string manipulation, and most I/O logic are abstracted away. This narrowing is what makes model generation tractable. The LLM does not need to emit a complete executable program; it only needs to make the concurrency architecture explicit. A deterministic checker then validates the resulting artifact against 61 rules organized into 9 categories, catching malformed or semantically inconsistent \textsc{Cir} artifacts before the more expensive verification phase.

% 因此,LLM 不能作为独立的验证器使用.并发错误是由独立合理的局部操作之间的组合交互驱动的.三线程循环死锁就是一个很好的例子:每个线程都可以以局部可理解的方式获取锁,但全局系统仍然会陷入循环等待.相关的交错操作数量会随着并发实体和同步操作数量的增加而迅速增长,而对该状态空间的穷举覆盖正是形式化方法不可或缺之处.在我们的架构中,LLM 负责执行恢复预期资源结构和同步意图所需的繁重语义工作,而形式化引擎则负责在有界模型内穷举探索由此产生的状态空间.这两个组件是互补的,而非可以互换的:LLM 提供抽象,而验证器则提供对交错操作的穷举推理.
LLMs are therefore not used as standalone verifiers. Concurrency bugs are driven by combinatorial interactions among independently plausible local actions. A three-thread circular deadlock is a useful illustration: each thread may acquire locks in a locally understandable way, yet the global system still reaches a cyclic wait. The number of relevant interleavings grows rapidly with the number of concurrent entities and synchronization operations, and exhaustive coverage over that state space is precisely where formal methods remain indispensable. In our architecture, the LLM performs the semantic heavy lifting required to recover intended resource structure and synchronization intent, while the formal engine takes over to explore the induced state space exhaustively within the bounded model. The two components are complementary rather than interchangeable: the LLM provides abstraction, and the verifier provides exhaustive reasoning over interleavings.

% 因此,形式化后端的选择至关重要.可以使用显式状态模型检查、有界编码或系统化的调度探索.诸如 SPIN 之类的显式状态框架功能强大,但通常需要专用的建模语言和额外的转换层 [Holzmann 1997 SPIN].有界编码可以有效地处理许多软件验证任务,但诸如条件变量唤醒语义、通道阻塞和信号量计数之类的同步结构并非总是最适合这种编码方式.动态和无状态探索技术仍然非常有价值,但它们与可执行工件和有界调度相关联,而不是与抽象的中间模型相关联 [Godefroid 1997 VeriSoft, Flanagan 2005 DPOR, Musuvathi 2008 FairStateless].相比之下,Petri 网为这种设置提供了一个自然的基础 [Murata 1989 PetriNets, Esparza 2008 Unfoldings].它们将并发性和资源争用结构化,配备了成熟的分析技术,并通过共享位置自然地组合.标准的P/T网本身不足以表达数据相关的分支,而经典的着色Petri网则在颜色域、绑定和铭文方面增加了大量的机制[Jensen2007CPNTools].我们的第二个形式化方法,并发验证网(Cvn),则处于中间位置:它是一个加权P/T Petri网,并添加了一个有限的全局变量存储和三值守卫.由于Cir已经通过全局命名明确了资源标识,因此令牌无需携带标识信息.这使我们能够在不达到着色令牌形式化方法的全部复杂性的情况下,捕获有界并发行为和数据相关的控制.
The choice of formal back-end is therefore central. One could use explicit-state model checking, bounded encodings, or systematic schedule exploration. Explicit-state frameworks such as SPIN are powerful, but they typically require a dedicated modeling language and an additional translation layer \cite{Holzmann1997SPIN}. Bounded encodings can handle many software-verification tasks effectively, yet synchronization constructs such as condition-variable wake-up semantics, channel blocking, and semaphore counts are not always the most natural fit for that style of encoding. Dynamic and stateless exploration techniques remain extremely valuable, but they are tied to executable artifacts and bounded schedules rather than to an abstract intermediate model \cite{Godefroid1997VeriSoft,Flanagan2005DPOR,Musuvathi2008FairStateless}. Petri nets, by contrast, offer a natural foundation for this setting \cite{Murata1989PetriNets,Esparza2008Unfoldings}. They make concurrency and resource contention structural, come with well-studied analysis techniques, and compose naturally through shared places. Standard P/T nets alone are not expressive enough for data-dependent branching, while classical colored Petri nets add considerable machinery in color domains, bindings, and inscriptions \cite{Jensen2007CPNTools}. Our second formalism, the \emph{Concurrency Verification Net} (\textsc{Cvn}), occupies a middle ground: it is a weighted P/T Petri net augmented with a finite global variable store and three-valued guards. Because \textsc{Cir} has already made resource identity explicit through global naming, tokens do not need to carry identity information. This allows us to capture bounded concurrency behavior and data-dependent control without moving to the full complexity of colored-token formalisms.

% Cir 生成和 Cvn 验证并非孤立步骤;它们构成了一个生成-验证-修复循环 \cite{Clarke2000CEGAR,Fan2023RepairFromLLMs,Bouzenia2025RepairAgent}.在 Cvn 状态空间搜索过程中发现的缺陷会生成一个结构化的反例:它能识别缺陷类型、提供跟踪信息、记录相应的 Cir 语句 ID,并汇总相关的最终状态信息,例如已占用的资源和等待的线程.由于反馈锚定于 sid 值而非模糊的自然语言描述,LLM 可以修改特定的同步逻辑,而无需重新生成整个工件.修复后的 Cir 随后会通过同一流程再次进行验证.验收并非仅基于无缺陷.只有在未发现并发冲突且用户声明的业务目标仍然可实现的情况下,修复才会被接受.这一附加要求至关重要,因为即使看似安全的修复方案通过静默删除必要行为来消除缺陷,它仍然可能是错误的.
\textsc{Cir} generation and \textsc{Cvn} verification are not isolated steps; they form a generate--verify--repair loop \cite{Clarke2000CEGAR,Fan2023RepairFromLLMs,Bouzenia2025RepairAgent}. A bug discovered during \textsc{Cvn} state-space search yields a structured counterexample: it identifies the bug kind, provides a trace, records the corresponding \textsc{Cir} statement IDs, and summarizes the relevant end-state information such as held resources and waiting threads. Because the feedback is anchored to $\mathsf{sid}$ values rather than vague natural-language descriptions, the LLM can revise specific synchronization logic instead of regenerating the entire artifact. The repaired \textsc{Cir} is then re-validated through the same pipeline. Acceptance is not based on bug-freedom alone. A repair is accepted only if no concurrency violation is found and the user-stated business goals remain reachable. Otherwise, an apparently safe repair may still be wrong because it eliminates the bug by silently deleting required behavior.

% 因此,本文的信任边界是生成的\textsc{Cir}工件,而非任意源代码.我们验证LLM生成的模型;我们并不证明源代码到\textsc{Cir}的通用等价性.这一边界既是一种限制,也正是它使得该方法易于分析.通过将语义模型构建与详尽的状态探索分离,该架构在LLM辅助的意图恢复和关于交错的正式推理之间创建了一个易于处理的接口.当前的原型在Rust示例上进行了评估,但核心的\textsc{Cir}/\textsc{Cvn}抽象是基于同步语义而非Rust特有的语法定义的.这项工作的实际动机是获得一个更易于分析的验证问题,方法是首先要求模型明确说明程序试图共享什么以及如何进行同步.
The trust boundary of the present paper is therefore the generated \textsc{Cir} artifact, not arbitrary source code. We verify the model that the LLM produces; we do not prove general source-to-\textsc{Cir} equivalence. That boundary is a limitation, but it is also what makes the approach analyzable. By separating semantic model construction from exhaustive state exploration, the architecture creates a tractable point of contact between LLM-assisted intent recovery and formal reasoning about interleavings. The current prototype is evaluated on Rust examples, but the core \textsc{Cir}/\textsc{Cvn} abstractions are defined over synchronization semantics rather than Rust-specific syntax. The practical motivation of the work is to obtain a verification problem that is easier to analyze by first asking the model to state explicitly what the program is trying to share and how it is trying to synchronize.

The contributions of this paper are as follows:
\begin{enumerate}
\item A model-first formulation of concurrency verification that shifts shared-resource identification from source-level alias reasoning to an LLM-generated verification artifact. The formulation does not claim to solve alias analysis in general; rather, it removes the need for the formal verification layer to perform that reasoning precisely.
\item \textsc{Cir}, a verification-oriented concurrency intermediate representation with global resource naming, explicit protection mappings, and statement-level anchors, together with a deterministic checker that enforces 61 well-formedness rules in 9 categories.
\item \textsc{Cvn}, a weighted P/T Petri net with a finite global store and three-valued guards, designed to capture bounded concurrency behavior without requiring the full complexity of colored-token formalisms when resource identity is already explicit.
\item A mechanical translation from \textsc{Cir} to \textsc{Cvn}, together with simulation-style correspondence results that support the soundness claims of the verification layer.
\item A two-layer generate--verify--repair architecture that combines fast \textsc{Cir} checking, exhaustive \textsc{Cvn} state-space search, structured counterexamples, and goal-aware acceptance to reject bug-free but semantically incomplete repairs.
\item An evaluation on 9 representative bounded-concurrency patterns showing how the pipeline behaves across generation, bug detection, repair, and goal-preservation stages.
\end{enumerate}
