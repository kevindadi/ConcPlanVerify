## Review

I audited the program against each requirement:

- **R1** — one main thread plus two spawned workers (`t1`, `t2`). ✔
- **R2** — both workers share the same `Arc<Mutex<()>>` instances for `a` and `b`; a `Mutex` cannot be held by two threads at once. ✔
- **R3** — each worker acquires `a` then `b` before doing its critical work, so both guards are alive simultaneously. ✔
- **R4** — `lock()` blocks until the mutex is free, then continues. ✔
- **R5** — both workers acquire locks in the **same global order (`a`, then `b`)**, so the circular-wait condition for deadlock can never arise. ✔
- **R6** — main calls `join()` on both handles before printing. ✔
- **R7** — the guards `_guard_a` and `_guard_b` are dropped at the end of the closure scope, i.e. before the thread finishes. ✔
- **R8** — with a consistent lock order and blocking acquisition, every interleaving terminates. ✔
- **R9** — exactly `DONE t1=1 t2=1` is printed, then the program exits. ✔

**Conclusion:** No concurrency defects found. The one defect class this pattern must avoid — inconsistent lock acquisition order (e.g., `t1` taking `a` then `b` while `t2` takes `b` then `a`) — is already prevented by using the identical order in both closures. The program is correct as written; I am returning it unchanged (with comments tightened for clarity).

## Complete program

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Shared resources: lock `a` and lock `b`.
    let a = Arc::new(Mutex::new(()));
    let b = Arc::new(Mutex::new(()));

    // Worker t1
    let a1 = Arc::clone(&a);
    let b1 = Arc::clone(&b);
    let handle_t1 = thread::spawn(move || {
        // Global lock order: a, then b. Blocking lock waits if busy (R4).
        let _guard_a = a1.lock().unwrap();
        let _guard_b = b1.lock().unwrap();

        // Critical work while holding BOTH locks (R3).
        // Guards drop here at scope end: both locks released before
        // the worker finishes (R7).
    });

    // Worker t2
    let a2 = Arc::clone(&a);
    let b2 = Arc::clone(&b);
    let handle_t2 = thread::spawn(move || {
        // Same global lock order: a, then b — no circular wait possible (R5, R8).
        let _guard_a = a2.lock().unwrap();
        let _guard_b = b2.lock().unwrap();

        // Critical work while holding BOTH locks (R3).
    });

    // Main thread starts both workers and finishes only after both finish (R6).
    handle_t1.join().expect("worker t1 panicked");
    handle_t2.join().expect("worker t2 panicked");

    // R9: exactly this line, then exit.
    println!("DONE t1=1 t2=1");
}
```

**Key invariant to preserve:** if either worker's lock-acquisition sequence is ever changed (e.g., `t2` taking `b` before `a`), R5/R8 would be violated and deadlock becomes schedulable. The consistent `a` → `b` order is the load-bearing fix.
