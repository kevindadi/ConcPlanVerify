## Defect review

The original program had each worker acquire the two locks in **opposite order** (t1: `a` then `b`; t2: `b` then `a`). That violates R5: a schedule exists where t1 holds `a` and waits for `b`, while t2 holds `b` and waits for `a` — a classic deadlock, so R8 also fails.

**Repairs, with justification:**

1. **Consistent lock ordering (fixes R5, R8):** Both workers now acquire `a` before `b`. With a global acquisition order, a circular wait is impossible, so no interleaving can deadlock and every schedule terminates.
2. **Blocking acquisition (R4):** `Mutex::lock()` blocks until the lock is free, then proceeds — a worker finding a lock busy waits and continues.
3. **Both locks held for critical work (R3):** Both guards are alive simultaneously during the critical section; a mutex can only be held by one thread at a time (R2).
4. **Guaranteed release (R7):** The guards are RAII (`MutexGuard`); they drop — releasing each lock — when the closure returns, even on early exit or panic of the *other* thread's logic path.
5. **Join before printing (R6, R9):** The main thread spawns both workers, joins both, and only then prints the required line.

## Repaired program

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Shared resources: a (lock), b (lock)
    let a = Arc::new(Mutex::new(()));
    let b = Arc::new(Mutex::new(()));

    // Worker t1: acquires locks in global order a -> b
    let a1 = Arc::clone(&a);
    let b1 = Arc::clone(&b);
    let handle_t1 = thread::spawn(move || {
        let _guard_a = a1.lock().unwrap(); // blocks until a is free (R4)
        let _guard_b = b1.lock().unwrap(); // blocks until b is free (R4)
        // Critical work: both locks held simultaneously (R3)
        // Guards drop here, releasing a then b (R7)
    });

    // Worker t2: acquires locks in the same global order a -> b
    let a2 = Arc::clone(&a);
    let b2 = Arc::clone(&b);
    let handle_t2 = thread::spawn(move || {
        let _guard_a = a2.lock().unwrap(); // same order: no circular wait (R5)
        let _guard_b = b2.lock().unwrap();
        // Critical work: both locks held simultaneously (R3)
        // Guards drop here, releasing a then b (R7)
    });

    // Main thread starts both workers and finishes only after both finish (R6)
    handle_t1.join().expect("worker t1 panicked");
    handle_t2.join().expect("worker t2 panicked");

    println!("DONE t1=1 t2=1");
}
```

**Why every schedule terminates (R8):** Since both threads request `a` first, at most one can hold `a`; the other blocks on `a` while holding nothing. The holder of `a` can always eventually acquire `b` (the other thread cannot hold `b` without first holding `a`), complete its critical section, and release both. No state exists in which each worker holds one lock and waits for the other, so deadlock is structurally impossible.
