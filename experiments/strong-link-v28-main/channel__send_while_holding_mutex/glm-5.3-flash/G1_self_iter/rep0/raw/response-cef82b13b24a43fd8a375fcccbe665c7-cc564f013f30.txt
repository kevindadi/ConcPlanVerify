## Defect review (what a naive version gets wrong, and the fix)

1. **Defect: holding the shared lock across a rendezvous channel operation.** With a zero-capacity channel (`sync_channel(0)`), `send` blocks until the peer calls `recv`. If `s` held the lock while sending on `ch1`, `r` could not take the lock to reach its `recv` — a classic deadlock (violates R3/R4). **Fix:** every mutex guard is confined to a tight `{ ... }` scope that ends *before* any channel call.
2. **Defect: circular wait across two channels.** If both roles did `send` first (or both `recv` first) on their respective channels, no rendezvous could ever complete. **Fix:** the protocol is asymmetric and complementary: `s` sends on `ch1` / receives on `ch2`; `r` receives on `ch1` / sends on `ch2`. The wait graph is a single chain, so every interleaving terminates (R4).
3. **Defect: lock order / shared-state races.** Only one lock exists, and `done` is written by exactly one role (`r`) and read by `main` only after `join`, so there is no data race and no lock-ordering hazard.

use std::sync::{Arc, Mutex};
use std::thread;

    // is a meeting point that blocks until both roles participate. (R2)

    let (tx2, rx2) = sync_channel::<i32>(0); // ch2

    // The one shared lock both roles occasionally use. (R1)

    let done: Arc<Mutex<i32>> = Arc::new(Mutex::new(0));

        // blocking send below — never wait on a channel while

        {

            *g += 1;
        }

## Why every interleaving terminates (R4)

- The lock is only ever held inside short critical sections that contain no channel operations, so neither role can block on a channel while the other is blocked on the lock (no deadlock via R3's invariant).
- The channel wait graph is acyclic: `s.send(ch1)` waits only for `r.recv(ch1)`; `r.send(ch2)` waits only for `s.recv(ch2)`. There is no cycle, so no circular wait is possible regardless of scheduling.
- Both threads are joined before printing, and `done` is written only by `r` before its ack rendezvous, so `main` always observes `1`.
