## Defect review

The naive design has each worker grab its locks in the order listed in R3:

- t1: `a`, then `b`
- t2: `b`, then `c`
- t3: `c`, then `a`

This violates **R5/R8/R9**: if each thread acquires its first lock and then yields, all three hold one lock and block waiting for the next — a classic circular-wait deadlock (t1 waits on b held by t2, t2 waits on c held by t3, t3 waits on a held by t1). Some interleavings would hang forever.

**Repair (justified):** impose a single global lock-acquisition order `a < b < c` and have every worker acquire its locks in ascending order. t1 takes `a`→`b`, t2 takes `b`→`c`, and t3 — which needs `c` and `a` per R3 — takes `a`→`c` instead of `c`→`a`. Circular wait is now structurally impossible (the wait-for graph is acyclic), so every schedule terminates (R5, R8, R9), while each worker still holds both locks simultaneously during its critical work (R4) and releases them before finishing (R6). Main joins all three workers before printing, satisfying R7, and prints exactly one line (R10).

## Repaired program

```rust
use std::sync::{Arc, Mutex};
use std::thread;

// Global lock order: a < b < c. Every worker acquires its locks in
// ascending order of this ranking, which makes circular wait impossible.

fn main() {
    let a = Arc::new(Mutex::new(0u64));
    let b = Arc::new(Mutex::new(0u64));
    let c = Arc::new(Mutex::new(0u64));

    // t1 needs a and b: acquire a, then b (ascending order).
    let t1 = {
        let (a, b) = (Arc::clone(&a), Arc::clone(&b));
        thread::spawn(move || {
            let mut ga = a.lock().unwrap();
            let mut gb = b.lock().unwrap();
            // Critical work: both locks held simultaneously.
            *ga += 1;
            *gb += 1;
            drop(gb);
            drop(ga);
        })
    };

    // t2 needs b and c: acquire b, then c (ascending order).
    let t2 = {
        let (b, c) = (Arc::clone(&b), Arc::clone(&c));
        thread::spawn(move || {
            let mut gb = b.lock().unwrap();
            let mut gc = c.lock().unwrap();
            // Critical work: both locks held simultaneously.
            *gb += 1;
            *gc += 1;
            drop(gc);
            drop(gb);
        })
    };

    // t3 needs c and a: acquire a, then c (ascending order — this is the
    // deadlock fix; the naive c-then-a order creates a circular wait).
    let t3 = {
        let (a, c) = (Arc::clone(&a), Arc::clone(&c));
        thread::spawn(move || {
            let mut ga = a.lock().unwrap();
            let mut gc = c.lock().unwrap();
            // Critical work: both locks held simultaneously.
            *ga += 1;
            *gc += 1;
            drop(gc);
            drop(ga);
        })
    };

    // Main starts all three workers and finishes only after all three finish.
    for handle in [t1, t2, t3] {
        handle.join().expect("worker thread panicked");
    }

    println!("DONE done=1");
}
```

## Why this meets every requirement

- **R1** — one main thread, three spawned workers (`t1`, `t2`, `t3`).
- **R2** — each lock is a `Mutex`; a mutex guard is exclusive by construction.
- **R3** — t1 uses `a`+`b`, t2 uses `b`+`c`, t3 uses `c`+`a` (acquired as `a` then `c`).
- **R4** — each worker performs its critical work only after holding both of its guards.
- **R5/R8/R9** — the strict global order `a < b < c` eliminates circular wait; any interleaving, including preemption between the two acquisitions, still terminates (a thread blocked on a later lock always releases its earlier one eventually, since the holder of the later lock never waits on the earlier one).
- **R6** — guards are explicitly dropped (and would also drop at scope end) before each worker returns.
- **R7** — main spawns all three and `join`s each before proceeding.
- **R10** — the only `println!` is the single line `DONE done=1`, printed after all joins.
