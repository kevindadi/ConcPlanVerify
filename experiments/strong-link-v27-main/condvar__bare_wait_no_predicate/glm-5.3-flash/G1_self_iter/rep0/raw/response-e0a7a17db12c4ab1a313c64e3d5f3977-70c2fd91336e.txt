## Review: defects found and repairs justified

Since the program under review exhibited the classic condition-variable defects, here is what was wrong and why each repair is required by the spec:

1. **Lost wakeup (violates R5, R7).** The original waiter checked the flag *without holding the lock*, then waited. If the notifier signaled between the check and the wait, the signal was lost and the waiter blocked forever. **Repair:** the flag check and the `wait` must happen atomically under `m` — the waiter locks `m` first, then waits while holding the mutex guard, so a signal that arrives before the wait cannot be missed (R5).

2. **Waiting while flag is true (violates R6).** The original used `if !ready { wait }` — a single check. **Repair:** a `while !*ready { wait }` loop, so the waiter never waits when the flag is already true and re-checks after every wake (R4, R6).

3. **Spurious wakeups (violates R9).** Condition variables may wake spuriously; an `if` would let the waiter proceed with the flag still false. **Repair:** the `while` loop re-locks `m` and re-tests `ready` after each wake, so the waiter cannot pass until the flag is genuinely true (R9).

4. **Holding the lock while blocked (violates R6).** A naive `lock(); wait();` without the guard-passing API deadlocks: the notifier can never acquire `m` to set the flag. **Repair:** `Condvar::wait` atomically releases `m` while blocked and re-acquires it before returning, so the waiter never holds `m` while blocked (R6).

5. **Flag set outside the lock (violates R3, R8).** The original notifier wrote `ready = true` without holding `m`, racing with the waiter's check. **Repair:** the notifier locks `m`, sets the flag, signals, and releases the lock by dropping the guard (R3, R8).

6. **Signal before lock release is fine** — `notify_one` while holding `m` is correct here; the woken waiter simply re-blocks on the mutex until the notifier's guard drops, then re-checks the flag. This preserves R3 exactly.

## Repaired program

```rust
use std::sync::{Arc, Condvar, Mutex};
use std::thread;

fn main() {
    // R2: one lock (m), one condition variable (cv), guarding the boolean flag (ready).
    let shared = Arc::new((Mutex::new(false), Condvar::new()));

    // R1: waiter role runs concurrently with the notifier role.
    let waiter = {
        let shared = Arc::clone(&shared);
        thread::spawn(move || {
            let (m, cv) = &*shared;
            // R4/R6: check the flag while holding the lock; wait only while false.
            // The guard is atomically released during wait and re-acquired on wake,
            // so the lock is never held while blocked.
            let mut ready = m.lock().expect("waiter: mutex poisoned");
            while !*ready {
                // R4/R9: re-check the flag after each wake (also covers spurious wakeups).
                ready = cv.wait(ready).expect("waiter: mutex poisoned");
            }
            // `ready` guard drops here, releasing m.
        })
    };

    let notifier = {
        let shared = Arc::clone(&shared);
        thread::spawn(move || {
            let (m, cv) = &*shared;
            // R3: set the flag while holding the lock, signal, then release the lock.
            let mut ready = m.lock().expect("notifier: mutex poisoned");
            *ready = true;
            cv.notify_one();
            drop(ready); // release m
        })
    };

    // R7: join both roles; every interleaving terminates because the waiter's
    // check-then-wait is atomic under m, so an early signal cannot be lost (R5).
    waiter.join().expect("waiter panicked");
    notifier.join().expect("notifier panicked");

    // R8/R10: the flag is true in every schedule; print the exact required line.
    let (m, _cv) = &*shared;
    let ready = *m.lock().expect("main: mutex poisoned");
    println!("DONE ready={}", ready);
}
```

**Why every schedule terminates (R7):** the waiter's flag test and its entry into `wait` occur while it holds `m`. The notifier can only set `ready = true` while holding `m`. Therefore either (a) the waiter observes `ready == true` on its first check and never waits, or (b) the notifier's flag-set-and-signal happens strictly after the waiter is already blocked in `wait` (with `m` released), so the signal is delivered and the waiter wakes, re-checks, sees `true`, and exits. There is no third interleaving, so both roles always finish and the program prints exactly `DONE ready=true` (R10).
