## Review notes (defects repaired and why)

1. **Lock held across a blocking rendezvous (deadlock, violates R3/R4).** A `MutexGuard` that is still alive when a thread calls `send`/`recv` on a rendezvous channel lets one role hold the shared lock while the other role needs it. Repair: every lock guard is confined to a `{ ... }` scope that ends *before* any channel operation.

2. **Wrong channel type (violates R2).** `std::sync::mpsc::channel()` is unbounded and buffered, so a send never forces a meeting. Repair: `sync_channel::<i32>(0)`, which is a true rendezvous — both roles must meet for the transfer to complete.

3. **Rendezvous-ordering deadlock on two channels (violates R4).** If both roles sent first on `ch1`/`ch2`, or both received first, some interleavings could block forever. Repair: the operations are crossed — `s` does *send on ch1 then recv on ch2*, `r` does *recv on ch1 then send on ch2* — which has no cycle, so every interleaving terminates.

4. **Single shared lock** (`shared`), used "occasionally" by both roles; a single mutex cannot self-deadlock, and since it is never held while channel-waiting, no lock-wait can block forever.

## Program

```rust
use std::sync::mpsc::sync_channel;
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // ch1 and ch2: rendezvous channels — both roles must meet to
    // transfer a value (R2). Capacity 0 makes the meeting mandatory.
    let (tx1, rx1) = sync_channel::<i32>(0);
    let (tx2, rx2) = sync_channel::<i32>(0);

    // The one shared lock both roles occasionally use (R1).
    let shared: Arc<Mutex<u64>> = Arc::new(Mutex::new(0));

    // Sender role: s
    let shared_s = Arc::clone(&shared);
    let s = thread::spawn(move || {
        // Occasional lock use; guard is dropped before any channel wait (R3).
        {
            let mut count = shared_s.lock().unwrap();
            *count += 1;
        } // lock released here

        // Rendezvous: blocks until r receives on ch1.
        // The shared lock is NOT held while waiting (R3).
        tx1.send(1).expect("role r terminated early");

        // Rendezvous the other way: blocks until r sends on ch2.
        let ack = rx2.recv().expect("role r terminated early");

        // Occasional lock use again (R1), never overlapping a channel wait.
        {
            let mut count = shared_s.lock().unwrap();
            *count += ack as u64;
        }
    });

    // Receiver role: r
    let shared_r = Arc::clone(&shared);
    let r = thread::spawn(move || {
        // Rendezvous: blocks until s sends on ch1. Lock not held (R3).
        let value = rx1.recv().expect("role s terminated early");

        {
            let mut count = shared_r.lock().unwrap();
            *count += value as u64;
        } // lock released before the next channel operation

        // Rendezvous: blocks until s receives on ch2.
        tx2.send(1).expect("role s terminated early");
    });

    // Both roles run at the same time; wait for both to finish (R1, R4).
    s.join().unwrap();
    r.join().unwrap();

    // The value exchanged over ch1 was 1 (R2, R5).
    println!("DONE done=1");
}
```

## Why every schedule terminates (R4)

- The only blocking primitives are the two rendezvous channel operations per role and the mutex.
- No thread ever holds the mutex while blocked on a channel, so the mutex is always eventually acquirable by whichever role wants it.
- The channel operations form a strict hand-off chain with no cycle: `s: send(ch1) → r: recv(ch1)` and `r: send(ch2) → s: recv(ch2)`. Since `s` sends before it receives and `r` receives before it sends, no interleaving can have both roles waiting on opposite ends of the same channel in a conflicting pattern.
- Therefore the worst-case interleaving still completes both rendezvouses, both roles finish, `join` returns, and the program prints exactly `DONE done=1` (R5) and exits.
