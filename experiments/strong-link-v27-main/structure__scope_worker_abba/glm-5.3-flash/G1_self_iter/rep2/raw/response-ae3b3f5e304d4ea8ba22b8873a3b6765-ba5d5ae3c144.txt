## Analysis of concurrency defects and their repairs

The classic defect in a program of this shape is **lock-order inversion**: one worker taking `a` then `b` while the other takes `b` then `a` creates a wait cycle (`w1` holds `a` waits for `b`; `w2` holds `b` waits for `a`), violating R5 and R7. The repair is to fix a single global lock order — both workers acquire `a` before `b` — which makes cycles impossible, since any worker holding `a` can always be waiting only on `b`, and `b` is always eventually released by its holder (R3). A secondary hazard is *not* releasing locks at all (R3): guard values dropped at scope end release the mutexes exactly once, and the `_` binding keeps the guards alive for the whole critical section so R2 ("holds both at the same time") is genuinely satisfied. Blocking `lock()` satisfies R6. Joining both handles before printing satisfies R8 and R9.

## Program

```rust
use std::sync::{Arc, Mutex};
use std::thread;

// Entities required by the spec:
//   roles:            w1, w2
//   shared resources: a, b (mutexes)

// R5: single global acquisition order a -> b for every worker.
// No worker ever acquires b before a, so a wait cycle
// (w1 holds a waits b, w2 holds b waits a) cannot form (R7).

fn worker(id: &'static str, a: Arc<Mutex<()>>, b: Arc<Mutex<()>>) {
    // R6: lock() blocks until the mutex becomes free.
    // Acquire in fixed order: a first, then b (R5).
    let _ga = a.lock().expect("mutex a poisoned");
    let _gb = b.lock().expect("mutex b poisoned");

    // R2: at this point the worker holds BOTH a and b simultaneously.
    // The guards `_ga` and `_gb` are kept alive by the `_` bindings
    // for the remainder of this scope, so both are genuinely held here.
    println!("[{}] holds a and b", id);

    // R3: `_ga` and `_gb` drop at scope exit, releasing each mutex
    // exactly once, in reverse acquisition order (b then a).
}

fn main() {
    // Shared resources; Arc allows both worker threads to access them.
    let a = Arc::new(Mutex::new(()));
    let b = Arc::new(Mutex::new(()));

    // R1: main starts exactly two workers contending for a and b.
    let h_w1 = {
        let a = Arc::clone(&a);
        let b = Arc::clone(&b);
        thread::spawn(move || worker("w1", a, b))
    };
    let h_w2 = {
        let a = Arc::clone(&a);
        let b = Arc::clone(&b);
        thread::spawn(move || worker("w2", a, b))
    };

    // R4: mutual exclusion is guaranteed by Mutex itself — at most one
    // worker can hold a given mutex at any moment.

    // R8: the group finishes only after BOTH workers have completed;
    // joining each handle blocks main until that worker terminates.
    h_w1.join().expect("w1 panicked");
    h_w2.join().expect("w2 panicked");

    // R9: exactly one line of output after both workers are done.
    println!("DONE done=1");
}
```

## Why every schedule terminates (R7)

Because both workers use the order `a → b`, any blocking point can only be `b` (a worker cannot block on `a` while holding nothing that another worker waits on... more precisely: a worker blocked on `a` holds nothing; the holder of `a` either holds nothing else or holds `a` alone and proceeds to take `b`; a worker blocked on `b` holds only `a`, and the holder of `b` holds nothing it needs to release later). The resource-allocation graph therefore never contains a cycle, so no deadlock is possible. Since mutexes are only ever held for a finite critical section (R3), every interleaving finishes and `main` joins both workers before printing.
