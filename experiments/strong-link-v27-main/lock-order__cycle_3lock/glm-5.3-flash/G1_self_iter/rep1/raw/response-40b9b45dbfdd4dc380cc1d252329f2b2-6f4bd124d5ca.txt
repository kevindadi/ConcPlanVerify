## Defect review

The naive design has each worker grab its locks in the order listed in R3: t1 takes `a` then `b`, t2 takes `b` then `c`, t3 takes `c` then `a`. That creates a **circular wait** (a → b → c → a), so an interleaving where each worker holds its first lock and blocks on its second violates R5, R8, and R9.

**Repair:** impose a global lock-acquisition order (`a` < `b` < `c`) and have every worker acquire in that order. t1 takes `a`,`b`; t2 takes `b`,`c`; t3 — which needs `c` and `a` — takes `a` **before** `c`. The cycle is broken: any worker that holds a lock always holds the lower-ordered one, so at least one worker can always acquire both of its locks and complete. R4 still holds (both guards are alive during the critical work), and R6 holds because Rust's RAII guards release on scope exit, before the thread closure returns.

## Program

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Shared locks a, b, c (R2: each held by at most one worker at a time).
    let a = Arc::new(Mutex::new(()));
    let b = Arc::new(Mutex::new(()));
    let c = Arc::new(Mutex::new(()));

    // Global acquisition order: a < b < c. This breaks the circular wait,
    // so no schedule can deadlock (R5, R8, R9).

    // t1 needs a and b: acquires a, then b.
    let (la, lb) = (Arc::clone(&a), Arc::clone(&b));
    let t1 = thread::spawn(move || {
        let _g1 = la.lock().unwrap(); // a
        let _g2 = lb.lock().unwrap(); // b
        // Critical work with both locks held (R4).
        // Guards drop here, releasing both locks before the thread ends (R6).
    });

    // t2 needs b and c: acquires b, then c.
    let (lb, lc) = (Arc::clone(&b), Arc::clone(&c));
    let t2 = thread::spawn(move || {
        let _g1 = lb.lock().unwrap(); // b
        let _g2 = lc.lock().unwrap(); // c
        // Critical work with both locks held (R4).
    });

    // t3 needs c and a: acquires a, then c (respects global order a < c).
    let (la, lc) = (Arc::clone(&a), Arc::clone(&c));
    let t3 = thread::spawn(move || {
        let _g1 = la.lock().unwrap(); // a
        let _g2 = lc.lock().unwrap(); // c
        // Critical work with both locks held (R4).
    });

    // Main starts all three workers and waits for all of them (R1, R7).
    t1.join().unwrap();
    t2.join().unwrap();
    t3.join().unwrap();

    // Exactly one line of output, then exit (R10).
    println!("DONE done=1");
}
```

## Why every schedule terminates

With the ordering `a < b < c`, suppose the workers run in any interleaving and all become blocked. Each blocked worker holds its lower-ordered lock and waits on a higher-ordered one. Consider the worker holding `a` (at least one must, or `a` is free and its seeker would have taken it). That worker waits only on `b` or `c` — never on `a` — so the wait graph is acyclic; some worker can always finish, release its locks, and progress cascades. Hence no deadlock under any interleaving, and `main` joins all three threads and prints the required line.
