```rust
// Auxiliary routine.
//
// R2: the spawned task captures nothing from `main`'s environment — there are
// no mutexes, counters, atomics, or statics shared between the main task and
// the helper task, so no two tasks ever contend for a resource.
//
// R3: `join()` guarantees this auxiliary call runs to completion before
// `helper` returns, so the caller cannot start its next call early.
//
// R4: the helper task is joined unconditionally on every call, so every
// schedule/interleaving terminates; there is no channel, lock, or loop that
// could deadlock or spin.
fn helper() {
    let task = std::thread::spawn(|| {
        // Purely local work: nothing is read from or written to any
        // state owned by the main task.
        let local: u32 = 1 + 1;
        std::hint::black_box(local);
    });
    task.join().expect("helper task must not panic");
}

fn main() {
    // R1: call the auxiliary routine, then begin the same call sequence again.
    helper();
    helper();

    // R2: `done` is a local variable of the main task only; it is never
    // shared with (or visible to) `helper`, so it is not shared state.
    let done = 1;

    // R5: exactly one line is printed, then the process exits.
    println!("DONE done={}", done);
}
```

**Concurrency-defect review and repairs (justification):**

1. **Defect risk: auxiliary work escaping the call boundary.** If `helper` spawned a task and returned without joining, two auxiliary calls could overlap and the main task could proceed before completion — violating R3 and making R4 schedule-dependent. **Repair:** `helper` joins its own task before returning, so each call is self-contained and runs to completion regardless of interleaving.

2. **Defect risk: shared coordination state.** A tempting design (a shared counter or mutex to track "done") would violate R2 and introduce contention/blocking that could deadlock under some interleavings (R4). **Repair:** all state is call-local; `done` lives only in `main` and is never touched by `helper`. The only synchronization is `join`, which is one-directional, cannot deadlock, and enforces R3.

3. **Defect risk: unbounded output or non-termination.** Loops or repeated printing inside `helper` could break R4/R5. **Repair:** `helper` performs only bounded local work and prints nothing; `main` prints the single required line after both call sequences finish, then exits.
