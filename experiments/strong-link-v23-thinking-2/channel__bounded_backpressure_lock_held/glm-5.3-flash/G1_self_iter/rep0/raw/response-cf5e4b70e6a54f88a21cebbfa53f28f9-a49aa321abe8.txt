## Analysis of defects to avoid

The classic concurrency bugs this design must prevent:

1. **Deadlock via lock-while-waiting (violates R5/R6):** calling a *blocking* `send`/`recv` while holding `m` can deadlock — e.g., sender holds `m` and blocks on a full channel while receiver needs `m` before it can drain the channel. Fix: every blocking channel operation happens strictly outside any `m` critical section (lock scopes are closed before send/recv).
2. **Lost ordering (violates R7):** an unbounded channel would let the sender push both values before the receiver takes the first. Fix: `sync_channel(1)` — a capacity-1 channel, so the second `send` cannot complete until the first value is taken (R2, R4, R7).
3. **Termination (R6):** with capacity 1 and exactly two sends/two receives, every interleaving is: send 1 → (recv 1 ∥ send 2 blocks) → recv 1 unblocks send 2 → recv 2 → both finish. No schedule can stall, since no thread ever blocks on the channel while holding `m`.

`m` is used "occasionally" by both roles to record progress and carry the `done` flag that main reads for the required output (R8).

```rust
use std::sync::mpsc::sync_channel;
use std::sync::{Arc, Mutex};
use std::thread;

// Shared state protected by the single lock `m` (R2).
struct State {
    done: bool,
    log: Vec<&'static str>,
}

fn main() {
    // ch: channel with capacity 1 (R2, R4, R7).
    let (tx, rx) = sync_channel::<i32>(1);
    // m: the one shared lock (R2).
    let m = Arc::new(Mutex::new(State {
        done: false,
        log: Vec::new(),
    }));

    // ---- sender role (R1) ----
    let m_sender = Arc::clone(&m);
    let sender = thread::spawn(move || {
        // Blocking send happens WITHOUT holding m (R5).
        // Buffer is empty, so this completes; buffer is now full.
        tx.send(1).expect("receiver alive");

        // Brief critical section; lock released at end of block.
        {
            let mut s = m_sender.lock().expect("m not poisoned");
            s.log.push("sent 1");
        } // m released BEFORE the next blocking send (R5).

        // Channel is full until the receiver takes value 1,
        // so this send waits — enforcing R7. Not holding m (R5).
        tx.send(2).expect("receiver alive");

        {
            let mut s = m_sender.lock().expect("m not poisoned");
            s.log.push("sent 2");
        }
        // Sender finishes (R3).
    });

    // ---- receiver role (R1) ----
    let m_receiver = Arc::clone(&m);
    let receiver = thread::spawn(move || {
        // Blocking recv happens WITHOUT holding m (R5).
        // Waits if channel is empty (R4).
        let first = rx.recv().expect("sender alive");

        {
            let mut s = m_receiver.lock().expect("m not poisoned");
            s.log.push("got 1");
        } // m released BEFORE the next blocking recv (R5).

        // Taking the first value is what unblocks the sender's
        // second send; then this recv finds value 2 (R3, R7).
        let second = rx.recv().expect("sender alive");

        {
            let mut s = m_receiver.lock().expect("m not poisoned");
            s.log.push("got 2");
            s.done = true;
        }
        let _ = (first, second);
        // Receiver finishes (R3).
    });

    // Main waits for both roles (R1, R3, R6).
    sender.join().expect("sender thread panicked");
    receiver.join().expect("receiver thread panicked");

    // Receiver has set done = true under m; read it under m (R8).
    let s = m.lock().expect("m not poisoned");
    assert!(s.done, "receiver must have finished");
    println!("DONE done={}", s.done as u8);
}
```

### Why every requirement holds

- **R1:** main spawns `sender` and `receiver`; they run concurrently.
- **R2:** `ch` is a `sync_channel(1)` (capacity exactly one); `m` is the single `Mutex` both roles lock.
- **R3:** exactly two sends and two receives; both threads run to completion.
- **R4:** `sync_channel` blocks on `send` when full and on `recv` when empty.
- **R5:** every `send`/`recv` call is lexically outside a `lock()` critical section — each critical section is a `{}` block that ends before the next channel operation.
- **R6:** the only blocking points are the capacity-1 channel operations, and the receiver never needs `m` to drain the channel, so no circular wait exists; all interleavings terminate.
- **R7:** with capacity 1, the sender's second `send(2)` cannot return until the receiver's first `recv` removes value 1.
- **R8:** main prints exactly `DONE done=1` (the `done` flag, set by the receiver under `m`, printed as `1`) and exits.
