Both workers already acquire `a` before `b`, so there is no lock-order deadlock in the original program. The version below makes that ordering explicit in one shared function; each worker holds both locks during its work, and Rust releases the guards before the worker returns.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn critical_work(a: &Mutex<()>, b: &Mutex<()>) -> usize {
    let _guard_a = a.lock().unwrap();
    let _guard_b = b.lock().unwrap();

    // Critical work while holding both locks.
    1
}

fn t1(a: Arc<Mutex<()>>, b: Arc<Mutex<()>>) -> usize {
    critical_work(&a, &b)
}

fn t2(a: Arc<Mutex<()>>, b: Arc<Mutex<()>>) -> usize {
    critical_work(&a, &b)
}

fn main() {
    let a = Arc::new(Mutex::new(()));
    let b = Arc::new(Mutex::new(()));

    let a1 = Arc::clone(&a);
    let b1 = Arc::clone(&b);
    let h1 = thread::spawn(move || t1(a1, b1));

    let a2 = Arc::clone(&a);
    let b2 = Arc::clone(&b);
    let h2 = thread::spawn(move || t2(a2, b2));

    let result1 = h1.join().unwrap();
    let result2 = h2.join().unwrap();

    println!("DONE t1={} t2={}", result1, result2);
}
```

The fixed acquisition order prevents circular wait. As with any thread-based program, termination assumes the scheduler eventually runs each worker.
